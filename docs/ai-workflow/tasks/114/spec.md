# 작업 명세: 클라이언트 AI 하네스 검증 흐름 개선

## 연결 정보

- 이슈: [#114](https://github.com/Project-Keeply/Keeply-Client/issues/114)
- 브랜치: `chore/ai-harness-workflow/#114`
- specRevision: 9

## 목적

설계와 검증·리뷰 맥락을 대화에만 의존하지 않고 파일로 전달한다.
AI가 새 대화에서 남은 작업을 파악하고 현재 변경에 유효한 결과를 기준으로
PR 준비 여부를 판단할 수 있도록 기존 클라이언트 하네스를 연결한다.

## 작업 범위

### 포함

- Notion 시작 스킬 제거 및 GitHub 이슈 기반 흐름 정리.
- 작업별 시작 조건·승인 범위·기본 리뷰·재검증 규칙 정리.
- 타입 검사 명령·리뷰 기준·스킬 경로·PR 제목 안내 정합성 수정.
- 명세·상태 템플릿과 사용자/메인 에이전트의 합의에 따른 업데이트 규칙.
- `logic-design`의 명세 저장과 복잡한 로직의 배치·패턴 선택을 돕는 설계 스킬.
- 공통 작업 복원, 검증·리뷰 증적, 미커밋/새 파일 리뷰 범위 처리.
- PR 준비 검사 및 `create-pr` 연결.
- 하네스 자체 검사·CI 연결·사용자 흐름 검증.

### 제외

- 서버 하네스와 Keeply-AX.
- API 연동 전용 스킬, 도구별 SessionStart hook, 명령 실행 guard.
- Notion 연동 및 동기화, subagent/worktree 자동화.
- 애플리케이션 기능 수정과 자동 커밋·머지.

## 설계 결정

- `docs/rules/ai-workflow.md`를 공통 정책의 기준으로 삼고 체크리스트·스킬에서 참조한다.
- 도구별 진입점은 유지하되 `CLAUDE.md`는 `@AGENTS.md`만 참조한다. 공통 규칙과 스킬 목록을 중복 관리하지 않는다.
- 남은 `create-issue`, `logic-design`, `branch-review`, `create-pr`의 책임을 유지한다.
- 작업 명세는 `docs/ai-workflow/tasks/{issue}/spec.md`로 공유한다.
- 실제 상태·검증 기록은 `.tmp/ai-workflow/tasks/{issue}/status.json`에 로컬로 저장한다.
- 메인 에이전트가 합의한 설계와 상태의 일관성을 관리하고 서브에이전트 결과를 통합한다.
- 단순 작업은 불필요한 패턴을 도입하지 않는다. 복잡한 로직은 책임·상태·API 경계를 검토한다.
- `logic-design`은 최초 명세를 저장하고, 이후 합의 변경은 공통 규칙으로 메인 에이전트가 갱신한다.
- 복잡한 책임·상태 혼재·역할별 분기·비동기 단계 또는 명시적 요청에만 `logic-architecture`를 참조한다.
- 서브에이전트는 설계 제안과 근거를 반환하며 공통 명세와 상태의 동시 편집은 피한다.
- 검사 대상은 HEAD뿐 아니라 작업 트리·기준 SHA·명세 버전·관련 환경을 고려한다.
- 누락·실패·오래된 기록은 통과로 인정하지 않는다. 기록이 없으면 실제 상태를 확인한다.
- 자동화 전 단계의 문서 규칙과 실제 실행 게이트를 명확히 구분한다.
- 복원 명령은 `pnpm workflow:resume`이다. 브랜치 또는 `--issue`에서 번호를 찾아
  로컬 명세·상태·Git 변경을 읽기 전용으로 요약하며 원격 조회와 상태 생성을 하지 않는다.
- 증적 대상에 파일 내용·index의 SHA-256 지문과 Node/pnpm/설치 상태 요약을 기록한다.
  지문·HEAD·기준 SHA·명세 버전·기록된 환경을 비교하며 외부 시스템 변화는 별도 확인한다.
- 검증은 `workflow:check`로 실제 실행 결과를 누적한다. 리뷰는 `workflow:review --start`로
  대상을 고정한 뒤 AI 판단을 입력·저장하며 수정 후 재리뷰 이력을 남긴다.
- PR 준비 명령은 읽기 전용 `pnpm workflow:pr-check`다. 명세·로컬 상태·실제 Git을
  비교해 준비 여부와 부족한 항목·다음 조치를 출력하며 검사 실행·상태 변경·원격 조회를 하지 않는다.
- 이슈·명세 연결, 작업 브랜치, 기준 ref, 커밋된 변경, 미커밋 변경 유무,
  완료 조건의 상태·근거, 변경 유형별 검증, 현재 리뷰와 미해결 결함을 함께 확인한다.
- 완료 조건을 `met`로 기록할 때 실제 근거와 함께 `subject` 및 `freshness`를 남긴다.
  현재 코드와 대상을 비교할 수 없는 기존 완료 기록은 재확인 대상으로 취급한다.
- 검증은 명령별 최신 실행 결과로 판단한다. 이전 실패는 보존하되 최신 성공을 막지 않고,
  최신 실패·누락·오래된 기록은 이전 성공으로 대체하지 않는다. N/A에는 적용되지 않는 이유가 필요하다.
- 문서 전용 작업은 문서 검토 결과와 앱 검사의 N/A 이유를 기록한다. 변경 유형별 추가 확인은
  `readinessEvidence`에 관측 이유·근거·대상 상태를 남기며 실제 수행 후에만 작성한다.
- 리뷰의 범위 누락·미확인 사항과 완료 조건의 실제 동작 충족은 에이전트가 판단·기록한다.
  준비 검사는 근거의 누락·불일치를 확인하며 외부 API·DB·환경변수의 정상 동작을 자동 보증하지 않는다.
- 리뷰 미확인 범위가 있으면 완료 조건에 영향이 없다고 판단한 이유와 근거를
  `unverifiedAssessment`에 기록한다. 이 판단이 없거나 근거가 부족하면 준비를 보류한다.
- `create-pr`은 준비 검사와 실제 게시 내용을 먼저 정리한 뒤 기존 게시 권한을 확인한다.
  자동 스테이징·커밋 및 기준 브랜치의 임의 대체는 하지 않는다. 승인된 예외는 통과와 구분한다.
- 하네스 지침·설정 검사는 읽기 전용 `pnpm workflow:harness-check`다. 공유 진입점·스킬
  메타데이터/등록·Claude 명령 링크·실제 로컬 문서 링크·실행 명령·빈 템플릿·CI 연결을 확인한다.
- 하네스 검사는 구조와 연결 관계를 대상으로 하며 자연어 지침의 의미나 실제 기능 적합성을
  자동 심사하지 않는다. 미지원/손상된 설정은 통과로 추정하지 않고 파일·이유·조치를 안내한다.
- 로컬 상태 파일·작업 이슈·기준 ref가 없는 checkout에서도 하네스 검사가 가능해야 한다.
  `.tmp`의 실제 기록은 검사 대상에서 제외하며 파일 쓰기·자동 수정·원격 조회를 하지 않는다.
- 하네스 검사는 `workflow:check`의 실행·기록 대상과 `workflow:pr-check`의 공통 필수 검사에
  연결한다. 문서 전용 작업의 앱 검사 N/A와 별개로 하네스 구조 검사를 확인한다.
- CI는 설치 후 하네스 검사 → 워크플로우 테스트 → lint → 타입 검사 → build를 실행한다.
  개발자 로컬 기록에 의존하는 PR 준비 검사와 상태 기록 명령은 CI에서 실행하지 않는다.
- 정상/오류 설정과 기록 부재·읽기 전용 동작을 임시 fixture로 검증하고 기존 워크플로우
  회귀 테스트에 포함한다. 실제 GitHub CI 실행 결과는 로컬 검증과 구분한다.
- 전체 사용자 흐름을 요청 예시·파일 저장 위치·실행 명령·차단 시 조치로 안내한다.
  임시 Git 저장소에서 실제 복원·하네스 검사·기록·리뷰 저장·PR 준비를 연결해
  증적이 없을 때의 차단, 유효한 문서 작업의 준비 통과, 변경 후 재차단을 확인한다.
  원격 이슈/PR 생성과 실제 CI 실행은 이 로컬 통합 검증에 포함하지 않는다.
- 리뷰 수집기는 실제 저장소의 `.tmp` 내부에만 산출물을 저장한다. 쓰기 전에 출력
  폴더의 각 경로와 기존 산출물 파일의 심볼릭 링크를 거부하고 실제 경로를 확인한다.

## 완료 조건

- AC-1: Notion 없이 GitHub 이슈부터 PR까지의 작업 절차와 권한 범위가 일관된다.
- AC-2: 안내된 검증 명령·리뷰 기준·문서 경로·PR 제목 형식이 실행 설정과 일치한다.
- AC-3: 대화에서 합의한 설계를 명세에 저장하고 변경 시 관련 결과의 재확인을 판단할 수 있다.
- AC-4: 로직 설계가 책임·상태 관리·필요한 패턴과 단순 대안을 검토하며 명세에 결정 이유를 남긴다.
- AC-5: 복원 기능이 작업·명세·변경·남은 작업을 보여주며 없는 기록을 성공으로 추정하지 않는다.
- AC-6: 미커밋 변경·새 파일도 리뷰 범위를 명시하고 현재 코드와 증적의 일치 여부를 확인한다.
- AC-7: PR 준비 검사가 누락·실패·오래된 결과와 미해결 결함을 발견하고 필요한 조치를 안내한다.
- AC-8: 하네스 검사와 CI가 설정 불일치를 발견하며 주요 정상·실패 흐름을 검증한다.

## 검증 방법

| 완료 조건 | 확인 방법 | 기대 결과 |
|---|---|---|
| AC-1 | 문서·스킬 교차 검토 | 작업별 진입 조건과 승인 규칙에 충돌 없음 |
| AC-2 | 명령·링크 확인, 리뷰 수집기의 정상/잘못된 ref 실행 | 실제 명령 존재, develop 기준 사용, 오류 안내 |
| AC-3 | 템플릿·업데이트 규칙·명세 저장 절차 확인 | 공유 명세와 로컬 상태 분리, 변경 이유와 재확인 규칙 존재 |
| AC-4 | 단순/복잡한 로직 설계 사례 검토 | 패턴 강제 없이 필요한 결정과 이유 기록 |
| AC-5 | 상태 존재/부재/불일치 작업 복원 실행 | 다음 단계와 미확인 상태를 정확히 표시 |
| AC-6 | staged/unstaged/untracked 변경 및 수정 후 증적 확인 | 범위 누락과 오래된 결과 발견 |
| AC-7 | 유효/누락/실패/변경된 결과로 PR 준비 검사 | 실제 준비 상태와 필요한 조치 구분 |
| AC-8 | 하네스 검사 정상/오류 사례 및 CI 설정 확인 | 설정 오류 발견, CI 실행 연결 |

완료 조건별 검토와 실제 정상·실패 실행 근거는 로컬 상태에 기록한다.
완료 조건 목록 자체는 통과 기록이 아니다. 원격 CI 실행 결과는 게시 후 별도로 확인한다.

## 미결정 사항

- 이슈 본문의 삭제 스킬 링크 항목과 추가 로직 설계 범위는 아직 정합성 업데이트가 필요하다.

## 주요 설계 변경

| specRevision | 변경한 결정 | 이유 |
|---|---|---|
| 1 | 기존 대화의 최종 합의로 최초 명세 작성 | 작업 인계와 구현 기준을 공유하기 위해 |
| 2 | 명세 갱신을 공통 책임으로 연결하고 복잡한 로직의 스킬 참조 조건 확정 | 스킬 재실행 없이 합의 변경을 반영하고 불필요한 패턴 검토를 줄이기 위해 |
| 3 | CLAUDE.md를 AGENTS.md 참조 진입점으로 단순화 | 도구별 지침과 스킬 목록의 중복 관리를 없애기 위해 |
| 4 | 읽기 전용 복원 명령과 불일치·기록 부재 처리 확정 | 현재 작업을 안전하게 이어받고 이전 결과를 통과로 추정하지 않기 위해 |
| 5 | 검증 실행 기록·리뷰 시작/저장·코드 및 환경 비교 설계 확정 | 기록의 성공 여부와 현재 변경에 대한 유효성을 구분하기 위해 |
| 6 | 읽기 전용 PR 준비 검사와 create-pr의 게시 전 확인 흐름 확정 | 최신 결과·완료 근거·현재 리뷰로 준비를 판단하고 게시 권한을 구분하기 위해 |
| 7 | 공유 하네스 구조 검사와 기록·PR 준비·CI 연결 확정 | 스킬·문서·명령의 연결 오류를 로컬과 CI에서 발견하고 도구 회귀를 확인하기 위해 |
| 8 | 사용 안내와 실제 로컬 명령을 연결한 통합 검증 확정 | 새 대화·기록 부재·검증/리뷰·게시 준비·변경 후 재확인을 하나의 흐름으로 확인하기 위해 |
| 9 | 리뷰 수집기의 실제 출력 경로와 기존 산출물 링크 차단 명시 | CodeRabbit 지적의 저장소 밖 산출물 쓰기를 재현하여 기존 저장 위치 정책을 보완하기 위해 |

최초 명세에는 Notion 제거, 공유 명세/로컬 상태 분리, 대화 기반 명세 갱신,
필요한 로직 설계 지원을 반영했다.
