# 클라이언트 로직 설계

공통 정책은 [AI Development Workflow](ai-workflow.md), 명세 갱신은
[작업 기록 규칙](../ai-workflow/README.md)을 따른다.
이 문서는 설계 판단 기준이며 애플리케이션 코드를 자동 변경하는 도구가 아니다.

## 적용할 때

`logic-design`에서 여러 책임이 섞인 로직, 서버/폼/화면 상태의 혼재,
역할별 처리 분기, 여러 비동기 단계, 서로 다른 도메인의 중복을 발견하면
`logic-architecture`를 참조한다. 사용자가 구조·패턴 검토를 직접 요청한 경우도 적용한다.
한 파일의 단순 표시·이벤트 수정은 추가 설계 절차 없이 기존 구조를 따른다.
복잡성은 파일 수가 아니라 상태·책임·의존성으로 판단한다.

## 기존 구조부터 확인

- 실제 `src/pages`, `src/features`, `src/entities`, `src/shared`의 관련 파일과 호출부를 읽는다.
  계층 이름만 보고 책임을 추정하지 않는다. 새 디렉터리 체계를 강제하지 않는다.
- 화면 구성은 기존 페이지·컴포넌트 경계를 따르고, 서버 상태는 기존 React Query
  훅과 query key factory를 우선 확인한다.
- 폼 상태·입력 검증은 기존 React Hook Form/Zod 사용처를 확인한다.
  작은 입력까지 라이브러리 사용을 강제하지 않는다.
- 서버 계약은 생성된 OpenAPI 타입과 도메인 타입 별칭을 확인한다.
  생성 파일을 수동 수정하지 않는다.
- 계산·변환·검증은 부작용 없는 함수로 분리할 가치가 있는지 검토한다.
  여러 도메인에서 실제로 같은 책임을 공유할 때만 `shared` 공통화를 제안한다.

## 설계할 내용

1. 완료 조건과 사용자 흐름을 구현 책임에 연결한다.
2. 서버 상태, 폼 상태, 화면 상태의 소유 위치를 정하고 불필요한 복제를 피한다.
3. 컴포넌트, 훅, API 함수, 변환 함수의 입력·출력·부작용을 구분한다.
4. 로딩, 빈 결과, 오류, 권한, 중복 제출, 취소/재시도 등 관련 예외만 검토한다.
5. 변경되는 호출부와 검증 방법을 설명한다.

## 패턴 선택

| 상황 | 검토할 선택지 | 더 단순한 대안 |
|---|---|---|
| 서버 응답과 화면 데이터가 다름 | Adapter 역할의 변환 함수 | 필요한 필드를 직접 사용 |
| 역할·종류별 처리가 독립적으로 바뀜 | Strategy 역할의 함수/맵 | 소수의 명확한 조건 분기 |
| 여러 단계와 잘못된 상태 조합이 있음 | 명시적 상태 전이·상태 유니온 | 단일 상태와 이벤트 처리 |
| 화면을 공통 조각으로 구성함 | Composition | 기존 컴포넌트 재사용 |

패턴은 이름이 아니라 해결할 실제 문제를 근거로 선택한다. 클래스, 레이어,
커스텀 훅, 상태 머신 라이브러리를 일괄 도입하지 않는다. 새 의존성이 필요하면
비용과 범위를 설명하고 합의한다. React Compiler 환경의 메모이제이션 규칙은
[Coding Convention](coding-convention.md)을 따른다.

## 결과와 범위

- 관련 파일과 실제 문제, 책임/상태 배치, 선택 이유와 단순 대안,
  예외·검증을 설명한다. 기존 구조 유지가 적절하면 그 이유를 적는다.
- 메인 에이전트는 합의한 결정을 작업 명세의 설계 결정·검증 방법에 반영한다.
  검토 중 제안은 미결정 사항으로 둔다. 기존 완료 조건 ID를 임의로 바꾸지 않는다.
- 서브에이전트는 지정한 범위를 검토하고 변경안을 보고한다.
  명세·상태를 동시에 편집하거나 push·PR을 수행하지 않는다.
- 이 스킬의 범위는 설계와 명세 문서다. 애플리케이션 구현은 별도 요청 범위에서 수행한다.
