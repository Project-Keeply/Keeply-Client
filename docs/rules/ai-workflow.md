# AI Development Workflow

GitHub Issues를 개발 작업의 기준으로 사용한다. 이 문서는 작업 시작 조건,
승인 범위, 기본 리뷰 기준, 재검증 조건의 기준 문서다.
스킬은 아래 규칙을 적용하고 작업별 실행 방법을 보충한다.

## 작업 흐름

1. GitHub 이슈를 생성하거나 선택한다. 새 이슈 생성은 `create-issue`가 담당한다.
2. `develop`에서 `{type}/{description}/#{issue-number}` 작업 브랜치를 만든다.
3. `logic-design`으로 구현 범위, 완료 조건, 검증 방법을 정리해 명세에 저장한다.
   복잡한 로직 구조는 `logic-architecture`를 참조한다.
4. 합의한 범위를 구현한다.
5. 변경에 필요한 검증을 수행하고 결과와 확인하지 못한 항목을 보고한다.
6. `branch-review`로 변경분을 리뷰하고 필요한 수정을 검증한다.
7. 준비 상태와 게시 권한을 확인한 후 `create-pr`로 PR을 생성하거나 수정한다.
8. GitHub CI와 팀 리뷰를 진행한다.

Notion은 이 흐름에 포함하지 않는다. 이슈 생성은 브랜치 생성이나 구현을
자동으로 허가하지 않는다. 각 단계는 Preflight → Flight → Postflight → Debrief를
따르되 아래 시작 조건에 맞는 확인만 수행한다.

## 작업별 시작 조건

| 작업 | 필요한 확인 | 진행 기준 |
|---|---|---|
| 이슈 생성 | 대상 저장소, GitHub 인증, 중복 이슈, 요청 범위 | 기존 이슈나 작업 브랜치를 요구하지 않는다. 현재 브랜치만으로 중단하지 않는다. |
| 브랜치 생성 | 대상 이슈, 기준 브랜치, 현재 변경, 동일 브랜치 존재 여부 | 기본 기준은 `develop`. 미커밋 변경을 자동으로 커밋·스태시·삭제하지 않는다. 변경이 있으면 인계 방법을 확인한다. |
| 설계 | 이슈, 관련 코드, 기존 변경, 알려진 요구사항 | 기본 브랜치에서도 읽기 전용 설계가 가능하다. 이슈가 없으면 미연결 상태를 표시하고, 명시적 설계 요청은 진행할 수 있다. |
| 구현 | 이슈 연결 작업 브랜치, 구현 범위, 완료 조건, 기존 변경 | `develop`/`main` 직접 구현 금지. 사용자 변경을 보존하고 승인된 범위만 수정한다. |
| 검증·리뷰 | 대상 변경, 기준 브랜치, 완료 조건, 기존 결과 | 기본 브랜치에서도 읽기 전용 확인이 가능하다. 사용자 관점은 추가 기준이며 없어도 기본 리뷰를 진행한다. |
| PR | 작업 브랜치, 대상 이슈·기준 브랜치, 커밋 상태, 검증·리뷰 결과, 게시 권한 | 미커밋 변경을 자동 스테이징하지 않는다. 누락·실패·오래된 결과를 먼저 알리고 해결하거나 명시적 예외를 남긴다. |

기능 작업의 설계·리뷰·PR 기준은 `develop`이다. `origin/develop`을 사용할 때는
실제 조회한 ref를 명시하고 최신 여부를 확인하지 못하면 그 한계를 알린다.
릴리스 등 다른 기준이 필요한 경우 대상 ref를 명시한다.

## 승인과 질문

- 사용자 요청과 이전 승인에서 이미 허가한 대상·범위·행동을 확인한다.
- 읽기, 상태 확인, 설계, 검증, 리뷰는 요청된 범위에서 별도 승인 없이 수행한다.
- 구현 전에는 범위와 영향받는 파일을 설명한다. 사용자가 이미 해당 범위의
  실행을 요청하거나 승인했다면 다시 승인받지 않는다.
- 요구사항, 외부 동작, 데이터 처리, 영향 범위가 실질적으로 달라지면 변경안을
  설명하고 추가 범위에 대한 승인을 받는다. 합의된 범위 안의 구현 방식과
  필요한 수정·재검증은 계속 진행한다.
- 이슈 생성, push, PR 생성·수정 등 외부 작업은 해당 행동의 권한을 확인한다.
  미승인 상태라면 대상과 실제 게시 내용을 준비해 프리뷰 후 승인받는다.
  이미 구체적으로 승인된 내용과 범위는 반복 확인하지 않는다.
- 기존 PR 본문 전체 교체는 교체 범위가 승인되었는지 확인한다.
  PR 생성 요청이 머지까지 허가하는 것은 아니다.
- 이미 대화·이슈·코드에서 확인되는 정보는 다시 질문하지 않는다.
  답이 없으면 진행할 수 없는 요구사항이나 범위 판단만 질문한다.
- 변경이 작아도 새 범위나 외부 게시 권한을 추정하지 않는다.

## 기본 리뷰 기준

작업 중 합의한 설계 변경은 스킬 재실행 없이 메인 에이전트가 명세에 반영한다.
자세한 절차는 [명세 유지 규칙](../ai-workflow/README.md)을 따른다.

사용자가 추가 관점을 주면 기본 기준에 함께 적용한다. 관점이 없으면 아래
기준을 사용하고 보고서에 "기본 리뷰 기준 적용"을 표시한다.

1. 이슈·합의한 완료 조건과 실제 동작의 일치 여부.
2. 상태·데이터 흐름, API 계약, 로딩·빈 결과·오류·권한·재시도 처리.
3. 변경의 기존 동작 영향, 호출부·타입·라우팅 연결, 관련 검증의 충분성.
4. 로직의 책임과 중복, 프로젝트 컨벤션 위반이 만드는 구체적 문제.

변경된 줄을 중심으로 필요한 호출부와 주변 코드를 확인한다. 단순 취향이나
패턴 적용 자체를 목적으로 리팩터링하지 않는다. 미커밋 변경과 새 파일의
누락 여부를 확인하고, 읽지 않은 변경까지 리뷰했다고 주장하지 않는다.
지적사항은 심각도, 파일·줄, 영향, 수정 제안으로 보고한다.
High/Medium의 미해결 결함은 PR 준비 완료로 판단하지 않는다.
Low는 처리 여부와 이유를 남긴다. 문제를 찾지 못한 경우에도 리뷰 범위와
확인하지 못한 항목을 명시한다.

## 검증과 재검증

| 변경 유형 | 필요한 확인 |
|---|---|
| 애플리케이션 코드·의존성·빌드 설정 | lint, 타입 검사, build 및 변경 기능에 필요한 기존 테스트·실행 확인 |
| UI 동작 | 위 코드 검증과 브라우저의 주요 흐름·관련 예외 확인 |
| 문서·스킬만 변경 | 링크·지침 일관성·diff 확인. 앱 lint/타입 검사/build는 N/A로 이유 표시 |
| 하네스 스크립트·검사 설정 | 변경 도구의 정상/실패 동작과 관련 CI 설정 확인 |

클라이언트 코드 검증 명령은 `pnpm lint`, `pnpm check-types`, `pnpm build`다.
PR 제목은 [Git Convention](git-convention.md)의 `[Type] description` 또는
`Type(scope): description` 형식을 따른다.

- 검사 결과에 실제 명령, 성공/실패/미실행/N/A, 대상 코드 상태와 범위를 남긴다.
- 실패·미실행은 통과로 인정하지 않는다. 환경상 확인할 수 없으면 한계와
  필요한 다음 확인을 명시한다. 예외로 PR을 게시한다면 사용자 승인과
  미확인 항목을 PR에 남기며 "검증 완료"라고 표시하지 않는다.
- 검증 이후 파일 내용, 새 파일, 의존성, 설정, 기준 브랜치가 바뀌면 영향을
  받는 검증과 리뷰를 다시 확인한다. 영향 판단이 불명확하면 해당 검사를 재실행한다.
- 커밋 해시가 같아도 작업 트리가 바뀌면 이전 결과를 그대로 사용하지 않는다.
  커밋만 달라지고 내용이 같다면 이전 결과의 대상과 내용 일치를 확인한다.
- 문서만 추가로 바뀌면 문서 검토를 다시 하고, 앱 내용·환경이 같은 경우
  앱 검증을 불필요하게 반복하지 않는다.
- 리뷰 지적을 수정하면 해당 문제의 해결 여부와 관련 검증을 재확인한다.

## 현재 구현과 예정 기능

현재 자동 실행 도구는 브랜치 diff 수집 스크립트와 GitHub CI다.
위 규칙은 AI가 문서를 읽고 수행하는 절차이며 자동 게이트가 아니다.
리뷰 수집기는 현재 커밋된 변경만 수집하므로 미커밋·새 파일은 별도 확인한다.

작업 명세·상태 템플릿과 업데이트 규칙은
[작업 기록 문서](../ai-workflow/README.md)에 정의되어 있다.
명세는 Git으로 공유하고 실제 상태는 `.tmp`에 로컬로 저장한다.
명세 저장·갱신은 현재 에이전트 지침으로 연결되어 있다. 별도 감시 프로그램은 없다.
상태 자동 갱신, 복원 스크립트, 검증·리뷰 증적 연결,
PR 준비 검사, 하네스 자체 검사는 이슈 #114의 후속 구현 단계다.
기록이 아직 없을 때는 현재 대화와 실제 Git 상태·검사 결과를 기준으로 보고한다.
