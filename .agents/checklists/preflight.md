# Preflight Checklist

기준: [AI Development Workflow](../../docs/rules/ai-workflow.md).
작업 종류에 해당하는 시작 조건만 적용한다.

## 1. 작업과 권한

- 요청이 이슈 생성, 브랜치 생성, 설계, 구현, 검증·리뷰, PR 중 무엇인지 파악한다.
- 대화에서 이미 정한 범위와 승인된 행동을 확인한다. 같은 범위를 반복 승인받지 않는다.
- AGENTS.md의 필독 문서와 해당 작업 규칙을 읽는다.
- 작업 재개 시 `pnpm workflow:resume`으로 명세·상태·변경을 확인한다.
  이슈 번호가 브랜치에 없으면 `--issue {번호}`를 사용한다. 기록 부재·경고를 통과로 해석하지 않는다.

## 2. 저장소와 변경

- 저장소와 `git status --short --branch`로 브랜치·현재 변경을 확인한다.
- 구현은 이슈 연결 작업 브랜치에서 수행한다. 이슈 생성·읽기 전용 설계·리뷰는
  기존 이슈나 작업 브랜치를 일괄 요구하지 않는다.
- 현재 변경과 사용자 작업을 보존한다. 자동 커밋·스태시·삭제하지 않는다.
- 작업 브랜치를 만들 때 기준 ref와 미커밋 변경의 인계 방법을 확인한다.

## 3. 이슈와 범위

- 이슈가 있으면 내용을 읽고 완료 조건·기존 설계를 확인한다.
- 구현에서 이슈 연결이 없으면 연결 방법을 확인한다.
- 이슈 없는 명시적 설계·리뷰 요청은 미연결 상태를 표시하고 진행할 수 있다.
- 기능 작업의 기준은 `develop`이며, 실제 사용한 로컬/원격 ref를 명시한다.
- 커밋된 diff 외에 staged/unstaged/untracked 변경도 확인한다.

## 4. 프리뷰와 질문

- 구현 전에 범위와 영향받는 파일을 설명한다.
- 이미 허가된 범위는 진행한다. 실질적 범위 변경이나 미승인 외부 행동은
  실제 변경안·게시 내용을 준비한 뒤 승인받는다.
- 리뷰 관점이 없으면 기본 기준을 사용한다.
- 이미 확인된 정보를 다시 묻지 않는다. 필요한 결정이 없을 때만 질문한다.
- 문서·스킬만 바꾸는 작업은 앱 검증이 N/A인지 판단하고 이유를 보고한다.
