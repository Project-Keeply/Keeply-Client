# 구현 설계와 명세 작성

[공통 워크플로우](../../../docs/rules/ai-workflow.md)와
[작업 기록 규칙](../../../docs/ai-workflow/README.md)을 따른다.
이 스킬은 애플리케이션 구현 대신 합의된 설계와 명세 문서를 작성한다.

## 1. 컨텍스트 확인

- `git status --short --branch`로 브랜치와 현재 변경을 확인한다.
- 브랜치의 `#{번호}` 또는 사용자가 지정한 이슈를 사용한다. 두 정보가 다르면
  대상 이슈를 확인한다. `gh issue view {번호} --json title,body`로 요구사항을 읽는다.
- 해당 `docs/ai-workflow/tasks/{번호}/spec.md`가 있으면 먼저 읽고 기존 합의를 보존한다.
- `git diff develop...HEAD --name-status`와 staged/unstaged/untracked 변경,
  관련 소스·호출부를 확인한다. 다른 기준 ref를 썼다면 명시한다.
- 이슈나 기준 ref를 읽지 못해도 제한된 설계가 가능하면 확인 범위를 알린다.
  구현을 좌우하는 정보가 부족하면 해당 항목만 질문한다.
- 기존 대화에서 확인한 범위와 승인을 재사용한다. 이슈가 없으면 설계를 대화에
  정리하고 저장 대상이 정해질 때까지 임의의 작업 폴더를 만들지 않는다.

## 2. 필요한 결정 정리

목적·포함/제외 범위·완료 조건·검증 방법부터 정리한다. 이미 확인된 내용을
다시 인터뷰하지 않는다. 필요한 경우만 파일 책임, 상태, API 계약, 라우팅,
로딩·빈 결과·오류·권한 처리를 사용자와 논의한다.

복잡한 책임 혼재, 상태 소유권, 역할별 분기, 비동기 단계가 있거나 사용자가
구조/패턴 검토를 요청하면 [logic-architecture](../logic-architecture/SKILL.md)를
참조한다. 단순 작업은 기존 구조를 유지하고 별도 패턴 검토를 강제하지 않는다.
이 참조는 서브에이전트 실행을 의미하지 않는다.

## 3. 명세 저장과 갱신

- 연결 이슈와 합의 범위가 있으면 [명세 템플릿](../../../docs/ai-workflow/templates/spec.md)을
  사용해 해당 작업 명세를 작성한다. 기존 파일은 필요한 섹션만 갱신하고
  파일 전체를 빈 템플릿으로 덮어쓰지 않는다.
- 저장은 요청된 설계 작업에 포함된다. 사용자가 읽기 전용·파일 수정 금지를
  지정했다면 대화에만 출력한다. 합의하지 않은 결정은 확정하지 않는다.
- 템플릿의 입력 표시를 실제 내용이나 이유 있는 N/A로 채운다. 미정 사항은
  미결정 섹션에 남긴다. 구현 순서를 고려한 구체적 파일·동작 계획을 적는다.
- 완료 조건의 고정 ID와 검증 방법 연결을 유지한다. 제거한 조건의 ID를 새
  조건에 재사용하지 않는다.
- 최초 명세는 `specRevision: 1`. 실질적 설계 변경은 버전을 올리고 이유를 남긴다.
  기존 구현·검증·리뷰와의 충돌 및 재확인 필요 사항을 함께 확인한다.
- 상태 파일이 있으면 작업 기록 규칙에 따라 영향받는 결과를 재확인 대상으로
  표시한다. 자동 지문 계산이나 증적 검사가 아직 구현되지 않았다면 실행했다고 주장하지 않는다.

## 4. 보고

한국어로 명세 경로, 주요 결정, 미결정 사항, 재확인할 검증과 다음 작업을
간단히 보고한다. 저장하지 못했거나 읽기 전용이면 그 상태를 명시한다.
명세 작성만으로 구현·검증이 완료됐다고 표시하지 않는다.
