# 클라이언트 로직 구조 검토

[로직 설계 기준](../../../docs/rules/logic-architecture.md),
[공통 워크플로우](../../../docs/rules/ai-workflow.md),
[명세 갱신 규칙](../../../docs/ai-workflow/README.md)을 읽고 적용한다.
이 스킬은 설계·명세만 다루며 애플리케이션 코드를 수정하지 않는다.

## 컨텍스트

대상 이슈·명세·완료 조건과 관련 소스·호출부를 확인한다. `logic-design`에서
이미 읽은 내용을 활용한다. 실제 경로와 현재 동작을 근거로 판단하고,
확인하지 못한 API 계약·사용자 의도는 가정과 구분한다.

## 설계 판단

- 기존 pages/features/entities/shared의 책임과 사용처를 먼저 파악한다.
- 서버 상태, 폼 상태, 화면 상태를 구분하고 소유 위치와 수명·무효화 방법을 정한다.
- 컴포넌트·커스텀 훅·API·순수 함수의 입력/출력과 부작용 경계를 설명한다.
- 기존 React Query/query key factory, React Hook Form/Zod, OpenAPI 타입,
  변환 함수 구조를 우선 활용한다. 단순한 로직은 기존 위치에서 유지할 수 있다.
- API 응답 변환, 독립적인 처리 분기, 복잡한 상태 전이, UI 조합에 실제 문제가
  있을 때만 Adapter/Strategy/명시적 상태 전이/Composition을 검토한다.
- 패턴을 선택하면 문제·대안·추가 복잡성·선택 이유를 설명한다. 클래스나 새
  라이브러리 도입을 패턴 적용의 조건으로 삼지 않는다.
- 로딩·오류·권한·중복 실행·재시도 등 관련 예외와 완료 조건의 검증 방법을 제안한다.

## 결과

관련 파일 → 현재 문제 → 책임/상태 배치 → 선택과 단순 대안 → 예외/검증을
한국어로 정리한다. 분리가 필요 없으면 기존 구조를 유지하는 이유를 설명한다.

메인 에이전트는 합의한 결정을 명세의 설계·검증 섹션에 반영하고 변경 버전과
재확인 필요 사항을 보고한다. 읽기 전용 요청은 문서를 수정하지 않는다.
서브에이전트로 위임된 경우 담당 범위의 근거와 제안만 반환한다. 공통 명세·
상태 편집, 브랜치 변경, push·PR은 수행하지 않는다. 이 스킬 자체는 위임 권한을 부여하지 않는다.
